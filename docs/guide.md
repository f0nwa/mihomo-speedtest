# Руководство по установке и настройке

Установщик и конфигурация Mihomo для роутеров на KeeneticOS с XKeen.
Отличие от типового конфига - собственный `speedtest2.sh`: он меряет
подписки по реальной пропускной способности, а не только по пингу (как
штатный `url-test` в mihomo), и по расписанию обновляет список самых
быстрых нод. Подробнее - в разделе [Speedtest](#speedtest-измеряем-реальную-скорость-а-не-пинг)
ниже.

`config.example.yaml` - обезличенный пример конфигурации созданный на основе конфигуратора rockblack, который автор далее дорабатывал под себя. 
Перед установкой скопируйте его в `config.yaml` и замените плейсхолдеры своими адресами, паролями и ссылками подписок. Рабочий `config.yaml` исключён из Git.

Конфигурация маршрутизирует трафик по сервисам: для каждого поддерживаемого сайта или приложения можно отдельно выбрать прямое подключение, автоматический прокси, резервную группу либо конкретный узел. Трафик, который не совпал ни с одним правилом, идёт напрямую.

## Установка с нуля

### Что нужно

- Роутер Keenetic с USB-накопителем, на нём установлен Entware.
- XKeen (проверить: `opkg list-installed | grep xkeen` или `xkeen -v`).
- Доступ по SSH под root.
- Одна-три ссылки на подписки в формате clash-yaml.
- Минимальные версии: XKeen - не ниже 2.0 (проверено на 2.0 Stable,
  сборка 2026-06-06), ядро Mihomo - не ниже 1.19.29, KeeneticOS - не
  ниже 5.1.4. Проверить свои версии: `xkeen -v` и `ndmc -c show version`.

Накопитель лучше брать не самый дешёвый: контроллер по выработке
ресурса может уйти в аппаратный read-only (в `dmesg` это выглядит как
`Sense Key 0x7 / ASC 0x27` и программно не лечится). Пока роутер не
перезагружали, mihomo продолжает работать из памяти, но любой ребут
поднимет старый конфиг.

Если XKeen ещё использует XRAY, сначала переключите его на mihomo:

```sh
xkeen -mihomo
```

Каталог конфига после этого - `/opt/etc/mihomo`, бинарь -
`/opt/sbin/mihomo`, кэши подписок падают в
`/opt/etc/mihomo/proxy-providers/`.

### Автоматическая установка

`setup.sh` копирует `config.example.yaml`, собирает ссылки подписок
(при повторном запуске предлагает перенести уже настроенные - подписки
регулярно умирают, см. раздел [Известные проблемы](#известные-проблемы)),
сам подбирает `User-Agent` для каждой через `detect_ua.sh`, предлагает
имя для каждого провайдера (сохранённое старое при переносе подписки
или собранное по домену ссылки для новой - в любом случае можно
подтвердить или переписать своим), применяет конфиг и передаёт
управление `install.sh` (speedtest). Перед стартом
оба скрипта проверяют версии из списка выше и жёстко останавливаются
при несоответствии.

### Применение конфига

Изменения в `config.yaml` применяются только через рестарт XKeen:

```sh
xkeen -restart
```

Валидацию без остановки работающего ядра делает `mihomo -t`:

```sh
/opt/sbin/mihomo -t -d /opt/etc/mihomo -f /opt/etc/mihomo/config.yaml
```

(то же самое умеет `xkeen -mtest`). Через API конфиг не применять -
`PUT /configs` на проверенной сборке роняет mihomo, роутер остаётся без
прокси до ручного рестарта.

После рестарта веб-морда доступна на `http://<IP роутера>:9090/ui`
(zashboard, скачивается автоматически по ссылке из конфига).

## Как работает маршрутизация

Mihomo проверяет правила сверху вниз и использует первое совпадение. Общая схема:

1. Реклама блокируется через `REJECT`.
2. QUIC блокируется для всех сервисов, чтобы клиенты перешли на обычное HTTPS-соединение поверх TCP.
3. Трафик известных сервисов попадает в соответствующие группы: `YouTube`, `Telegram`, `Spotify`, `AI`, `KinoPub` и другие.
4. Российские домены из `category-ru@domain` идут через `DIRECT`.
5. Трафик крупных CDN попадает в группу `CDN`.
6. Последнее правило `MATCH,DIRECT` отправляет весь оставшийся трафик напрямую.

Порядок важен. Например, правило блокировки рекламы стоит первым, поэтому оно срабатывает раньше правил отдельных сервисов.

### Блокировка QUIC

Провайдер правил `quic@inline`, заданный прямо в конфигурации, находит весь UDP-трафик, направленный на порт `443`. Правило `RULE-SET,quic@inline,REJECT` стоит в начале списка и блокирует такой трафик до проверки правил отдельных сервисов.

QUIC и HTTP/3 работают поверх UDP. После блокировки большинство браузеров и приложений повторяют подключение через HTTPS поверх TCP. Это позволяет Mihomo обрабатывать соединение по обычным правилам маршрутизации. Блокировка действует глобально, а не только для YouTube. Клиент, который не умеет переключаться на TCP, не сможет установить соединение.

## Основные группы прокси

| Группа | Что делает |
|---|---|
| `⚡ Самые быстрые + Fallback` | Приоритет 1: внутренний пул `⚡ Быстрый пул` (узел с минимальной задержкой из локального провайдера `fast`, список хранится в `fast.yaml`). Приоритет 2: если быстрый пул недоступен, используется `🛡️Fallback-Stable`. Если недоступны оба, соединения завершаются ошибкой - автоматического DIRECT нет. `⚡ Быстрый пул` виден в дашборде как обычная группа (с живыми нодами из `fast.yaml` и их пингами), но не входит в списки сервисных групп и недоступен для ручного выбора. |
| `🚀 Авто по пингу` | Проверяет узлы из трёх подписок и двух статических Hysteria2-прокси, затем выбирает узел с минимальной задержкой. |
| `🛡️Fallback-Stable` | Использует первый доступный узел и переключается на следующий, если текущий перестал отвечать. |
| `⚙️Manual` | Позволяет вручную выбрать `DIRECT`, статический Hysteria2-прокси или узел из подписки. |
| `Заблок. сервисы` | Общий выбор для сервисов, которым обычно нужен прокси. По умолчанию использует группу `⚡ Самые быстрые + Fallback`. |

Список `fast.yaml` для группы `⚡ Самые быстрые + Fallback` собирает не сам Mihomo, а
отдельный замерщик `speedtest2.sh` - как именно он это делает, см. раздел
[Speedtest](#speedtest-измеряем-реальную-скорость-а-не-пинг) ниже.

Ручной выбор `DIRECT` или отдельного узла в `⚙️Manual` - осознанный обход, на
который этот резерв не распространяется: пользователь сам отвечает за
работоспособность выбранного вручную варианта.

### Интервалы проверок доступности

Интервал выбирайте по числу нод после объединения всех подписок и применения
`exclude-filter`, а не по числу самих подписок. Одна крупная подписка может
нагрузить роутер сильнее нескольких небольших.

| Проверка | Размер пула | Рекомендуемый интервал | Минимум |
|---|---:|---:|---:|
| Провайдер `fast` | до 20 нод | 60 с | 60 с |
| Внутренняя группа `⚡ Быстрый пул` | до 20 нод | 60 с | 60 с |
| Внешняя группа `⚡ Самые быстрые + Fallback` | вложенные группы | 600 с | 300 с |
| `🚀 Авто по пингу` | полный пул подписок | 600 с | 300 с |
| `🛡️Fallback-Stable` | полный пул подписок | 600 с | 300 с |
| Health-check провайдеров подписок | полный пул каждого провайдера | 300 с | 300 с |

Для 100 и более нод ставьте `interval: 600` у массовых групп, включая
`🛡️Fallback-Stable`. Не копируйте минутный интервал из маленького `fast`
в группы, которые проверяют все ноды подписок.

Практический замер на четырёхъядерном Keenetic с 185 нодами показал, что
минутный цикл массовых проверок занимал 2,7-3,9 ядра до 20 секунд. Когда
циклы нескольких групп совпадали, росла нагрузка Mihomo, а запросы
XKeen к API групп прокси завершались ошибкой 504. Перезапуск снимал
симптом, но не устранял причину.

Провайдер `fast` и группа `⚡ Быстрый пул` используют один URL и могут
оставаться на 60 секундах: Mihomo не создаёт для этой пары вторую
независимую provider-проверку. Внешняя fallback-группа способна при своей
проверке обратиться к обеим дочерним группам, поэтому минутный интервал для
неё не подходит. Мастер-группа `Заблок. сервисы` и сервисные
`select`-группы своих проверок не делают.

Все проверки используют `lazy: true`: неиспользуемая группа или провайдер
не запускает очередной плановый цикл. Но активная вложенная группа всё равно
может вызвать проверки дочерних групп, а при отказах возможны внеочередные
попытки. `timeout: 5000` ограничивает ожидание ответа от одной ноды пятью
секундами. Он не задаёт частоту проверок и не ограничивает длительность всего
цикла. В Mihomo 1.19.29 это значение используется по умолчанию, а явная запись
в шаблоне фиксирует ожидаемый предел при будущих обновлениях.

### Обновление существующей установки

Резерв для `⚡ Самые быстрые + Fallback` действует только в конфигах, сгенерированных
из поставляемого шаблона `config.example.yaml` начиная с этой версии.
`install.sh` разворачивает и обновляет только сам спидтест (`speedtest2.sh`
и связанные файлы) поверх уже существующего `config.yaml` - он не является
универсальным мигратором маршрутизации и не переписывает чужую схему
групп. Если у вас уже развёрнутый роутер со старым `config.yaml`:

1. Прогоните `setup.sh` заново поверх текущей установки - он предложит
   перенести уже настроенные подписки (см. [Автоматическая
   установка](#автоматическая-установка)) и применит актуальный шаблон
   групп и проверок.
2. Обязательно посмотрите diff между старым и новым `config.yaml` перед
   применением - `setup.sh` не подменяет ваш рабочий конфиг молча.
3. Если вы используете собственный, самостоятельно написанный TEMPLATE
   вместо поставляемого `config.example.yaml`, эта гарантия резерва на
   него не распространяется - схему групп и проверок в таком шаблоне
   нужно перенести самостоятельно.
4. Если на роутере отдельно установлена сторонняя панель Xkeen UI и в ней
   включена "Защищённая DNS Mihomo" (или DNS-over-VLESS для Xray),
   `setup.sh` перед перезаписью `config.yaml` это обнаружит и спросит
   подтверждения. Существующий блок `dns:` переносится как есть, но сама
   панель хранит хэш всего файла на момент включения своей защиты - после
   перезаписи он неизбежно разойдётся. После установки **не нажимайте
   "Восстановить" в панели Xkeen UI** - это откатит её собственный старый
   снимок и затрёт результат `setup.sh`; если статус защиты в панели
   собьётся, просто включите её заново тем же способом, каким включали в
   первый раз. Для неинтерактивных прогонов проверку можно пропустить
   через `SKIP_DNS_GUARD_CHECK=1` (ответственность за то, что делать с
   чужим DNS-блоком, в этом случае берёт на себя тот, кто запускает).

Группы сервисов наследуют один набор вариантов выбора:

```text
DIRECT
Заблок. сервисы
🚀Auto-Best
🛡️Fallback-Stable
⚙️Manual
```

Поэтому, например, YouTube можно направить через общий режим для заблокированных сервисов, отдельный автоматический выбор, стабильный резерв, конкретный узел или напрямую.

У групп `Meta` и `CDN` также есть вариант `PASS`. Он пропускает текущее совпадение и продолжает проверять следующие правила. Это не то же самое, что `DIRECT`.

## Speedtest: измеряем реальную скорость, а не пинг

Штатный `url-test` в mihomo меряет только задержку - ядро дёргает
`generate_204` и не читает тело ответа, скорость канала оно не знает в
принципе. Сторонний `clash-speedtest` (faceair) не умеет xhttp и
показывает такие ноды как стопроцентные потери. В обоих случаях нода с
пингом 40 мс и полосой 0.5 МБ/с спокойно обгоняет ноду с пингом 90 мс и
15 МБ/с.

`speedtest2.sh` решает это, измеряя тем же ядром mihomo, что стоит на
роутере, и умеет ровно те транспорты, что установлены:

1. Разбирает `proxy-providers` из рабочего `config.yaml`, каждую ноду
   кладёт отдельным файлом.
2. Поднимает второй, отдельный от боевого, экземпляр mihomo (порты
   7899/9099) - рабочее ядро при этом не трогается.
3. Одним запросом отсеивает мёртвые ноды (сотня нод - за пять секунд),
   затем по живым от меньшей задержки переключает селектор и реально
   скачивает 10 МБ через каждую.
4. Победителей проверяет через `mihomo -t`, сравнивает с текущим
   `fast.yaml` и публикует только при изменении состава - атомарно,
   через временный файл и `mv`.

Дополнительно:

- мягкий режим отбора: `MAX_PING_MS=500` исключает из скоростного теста
  ноды с большей задержкой; `MAX_TESTED=40` ограничивает число кандидатов
  после сортировки по пингу. Значение `0` отключает соответствующий лимит.
  Проверка задержки пока охватывает весь пул, поэтому эти настройки не
  ограничивают её параллелизм и проверки подписок в боевом Mihomo;
- `ENOUGH=20` завершает загрузки раньше, если найдено 20 уникальных нод
  выше порога скорости; `TOPN=15` ограничивает итоговый быстрый пул.
  Добор до `MIN_WINNERS=3` использует только протестированных кандидатов
  и не возвращает ноды, отсеянные по пингу. Если кандидатов или рабочих
  результатов нет, сохраняется прежний `fast.yaml`, даже если его ноды
  уже не соответствуют новому порогу задержки;
- лимиты доступны в веб-настройках и сохраняются в `speedtest2.env`.
  Повторная установка сохраняет ранее заданные лимиты; новые значения
  по умолчанию не заменяют пользовательские `TOPN` и `ENOUGH`;

- порог отбора калибруется по скорости прямого канала при установке
  (`install.sh --recalibrate` - пересчитать без переустановки);
- в `fast.yaml` всегда попадает не меньше `MIN_WINNERS` нод (по
  умолчанию 3), если только для этого есть из чего выбрать: если порог
  скорости прошло меньше, добор идёт из остальных РАБОЧИХ (реально
  ответивших) нод по убыванию скорости - полностью нерабочие в добор не
  попадают. Пустой прежний `fast.yaml` не трогается только если вообще
  ни одна нода не ответила - оставлять там уже неживую с прошлого
  прогона ноду смысла нет;
- по умолчанию запускается по cron раз в три часа, внеплановый ручной
  прогон - `speedtest2.sh --force` (живой вывод в терминал, снятие
  зависшей блокировки при повторном запуске);
- каждый прогон пишет строку в `speedtest_runs.tsv` (сводка: канал,
  порог, счётчики нод) и `speedtest_history.tsv` (ноды-победители);
- после каждого прогона обновляется `stats.html` (оба графика -
  "Ноды" и "Скорость нод-победителей по прогонам" - при наведении
  курсора показывают вертикальную линию, точки ближайшего прогона и
  тултип с датой и значениями; на графике по нодам-победителям
  дополнительно подсвечивается линия ближайшей к курсору ноды, а
  остальные затемняются - удобно разглядеть конкретную ноду среди
  восьми; под каждым графиком - статичная строка Мин/Р95/Макс/Сейчас
  (по линии "нод выше порога"/"победителей" на первом графике, по всем
  показанным нодам вместе на втором); таблица последнего замера,
  светлая/тёмная тема с переключателем, без внешних JS/CSS-зависимостей)
  и раздаётся отдельным веб-сервисом на своём порту, не связанным с
  zashboard/API mihomo: `http://<IP роутера>:8899/` (или `/stats` - то же
  самое, адрес после слеша не важен для этой страницы). Если на роутере
  есть `python3` - веб-сервис поднимается на нём (`stats_httpd.py`) и
  отдаёт этот новый интерфейс с чистыми адресами (`/`, `/stats`,
  `/settings`) плюс старый `/stats.html` тоже продолжает работать. Без
  `python3` веб-сервис автоматически откатывается на резервный
  `busybox httpd` - тогда доступен только старый `/stats.html`.
  `install.sh` сам пытается поставить `python3` через `opkg` при установке
  (см. ниже); если это не удалось или `python3` появился позже другим
  путём - `sh speedtest2.sh --force` без переустановки поднимает уже
  новый интерфейс. Порт настраивается через
  `STATS_HTTP_PORT` в `speedtest2.env`, `STATS_HTTP_ENABLE=0` отключает
  веб-сервис совсем. Автозапуска после перезагрузки роутера пока нет (см.
  `TODO.md`) - сервис поднимается заново при первом же прогоне по cron
  после перезагрузки;
- по ссылке «Настройки» в шапке страницы (или напрямую
  `http://<IP роутера>:8899/settings` - на резервном `busybox httpd` без
  `python3` тот же адрес будет `.../cgi-bin/config`) открывается форма:
  - гео-фильтр (`BLOCK`) - тот же обязательный фильтр, что при установке
    просит `install.sh`; форма подсказывает варианты `exclude-filter`,
    заново найденные `providers.awk` в текущем `config.yaml`;
  - параметры самого замера: какие типы нод не тестировать вовсе
    (`EXTYPE`), размер файла и таймаут закачки на ноду (`SIZE`/`DL_TIMEOUT`,
    в форме - в МБ/сек), порог отбора и его составляющие
    (`MIN_SPEED`/`MIN_RATIO`/`MIN_FLOOR`), сколько нод класть в
    `fast.yaml` и минимум даже ниже порога (`TOPN`/`ENOUGH`/`MIN_WINNERS`)
    - подробности каждого см. в комментариях у соответствующей переменной
    в шапке `speedtest2.sh`;
  - сколько нод показывать на графике (`STATS_NODE_CAP`, 1-8), сколько
    хранить прогонов/дней истории
    (`HISTORY_KEEP_RUNS`/`HISTORY_KEEP_DAYS`) и логин/пароль для самой
    этой формы (`STATS_AUTH_USER`/`STATS_AUTH_PASS` в `speedtest2.env`,
    Basic Auth только на `/cgi-bin` - сам `stats.html` всегда открыт без
    пароля);
  - окно и срок хранения для таблицы "Доступность нод пула"
    (`STABILITY_WINDOW`/`STABILITY_DROP_AFTER` - длина окна "недавних"
    прогонов в `node_stability.tsv` и через сколько прогонов подряд без
    ноды в пуле строка удаляется).

  Все значения пишутся в `speedtest2.env` тем же способом, что и
  `install.sh`, и действуют с ближайшего прогона (по cron или по кнопке
  «Запустить прогон сейчас»); сохранение сразу перегенерирует
  `stats.html` и при необходимости перезапускает веб-сервис (например,
  при смене пароля) - остальные параметры (гео-фильтр, пороги отбора и
  т.п.) на сам веб-сервис не влияют.
- отдельно от графиков скорости - таблица «Доступность нод пула»: по
  каждой ноде пула (не только победителям `fast.yaml`) статус на
  последнем прогоне, uptime за окно последних прогонов (по `delay-check`,
  весь пул каждый прогон), спарклайн, средняя скорость и дата первого
  появления; клик по заголовку колонки сортирует таблицу. Средняя
  скорость - среднее всех замеров этой ноды, в скобках рядом -
  отклонение последнего замера от этого среднего; считается только по
  нодам, хоть раз прошедшим speed-тест - он идёт не по всему пулу каждый
  прогон (см. `ENOUGH` выше), поэтому у части нод в этой колонке будет
  «-», даже если по `delay-check` они «живы». Данные копятся в
  `node_stability.tsv` (агрегат - одна строка на ноду, `STABILITY_WINDOW`
  прогонов в окне, `STABILITY_DROP_AFTER` прогонов подряд без ноды в
  пуле - строка удаляется).

Установка (на роутере, из каталога с `install.sh`, `speedtest2.sh`,
`prep.awk`, `providers.awk`):

```sh
cd /opt/etc/mihomo   # или каталог, куда скопированы все четыре файла
sh install.sh
```

Установщик сам разбирает `proxy-providers:` в `config.yaml`, собирает
`SOURCES`, ищет гео-фильтр (при отсутствии запросит вручную, без
фильтра установка не продолжится), калибрует порог скорости от прямого
канала, раскладывает файлы, ставит cron и делает пробный запуск.
Результат - файл `speedtest2.env` рядом с `config.yaml`. Перекалибровать
порог без повторной установки:

```sh
sh install.sh --recalibrate
```

Первый запуск руками, потом смотреть лог:

```sh
/opt/etc/mihomo/speedtest2.sh
cat /opt/etc/mihomo/speedtest.log
cat /opt/etc/mihomo/speedtest_last.txt   # полная таблица замера
```

Прогон занимает 60-70 секунд. Блокировка запуска хранится в
`/tmp/mst.lock`; если прошлый запуск ещё работает, новый (без `--force`)
просто пишет предупреждение и завершается без измерений.

### Перенос файлов на роутер и обновление после правок

Три отдельных шага, и все три обязательны - если пропустить любой,
будете смотреть на старую версию и решите, что фикс не сработал (так
уже бывало, см. историю в CHANGELOG.md): **1) скопировать файлы на
роутер, 2) применить (перезапустить), 3) проверить, что роутер реально
отдаёт новое**. `git commit`/`git push` на рабочей машине - это только
сохранение истории, сам по себе на роутер он ничего не переносит.

`install.sh` и `speedtest2.sh` сами по себе тоже ничего не переносят на
роутер - копирование (шаг 1) это разовое (и при каждом обновлении
скриптов - повторное) действие с рабочей машины. SSH под root уже нужен
для установки (см. выше), поэтому проще всего `scp`.

Если SSH на роутере висит не на стандартном 22-м порту (проверить: как
вы обычно к нему подключаетесь) - добавить `-P <порт>` к `scp` и
`-p <порт>` к `ssh` (регистр разный у этих двух утилит - не опечатка).

Ещё одна частая заминка именно на Entware: свежий `scp` (например, из
современного macOS) по умолчанию сперва пробует протокол SFTP, а на
роутере может не быть `sftp-server` - тогда команда падает с
`sh: /opt/libexec/sftp-server: not found` / `scp: Connection closed`.
Лечится флагом `-O` (заставляет `scp` использовать старый scp-протокол,
`sftp-server` для этого не нужен).

**Шаг 1 - копирование.** С рабочей машины, из каталога с исходниками
проекта - список файлов тот же, что и в проверке "все файлы на месте" в
начале `main()` в install.sh (если туда добавили новый файл - добавить
и сюда, иначе `scp` этим списком тихо не довезёт его до роутера, а
write_stats_static()/install.sh будут смотреть на старую версию или
вовсе ничего не найдут):

```sh
scp -O -P <порт SSH, если не 22> install.sh speedtest2.sh prep.awk \
    providers.awk render_stats.awk stats_cgi.sh stats_run.sh \
    stats_httpd.py stats_index.html stats_style.css stats_app.js \
    stats_chart.js node_stats_update.awk sub_convert.awk render_progress.awk \
    root@<IP роутера>:/opt/etc/mihomo/
```

`config.yaml` и `speedtest2.env` этой командой не трогать - они у
роутера свои (`config.yaml` содержит реальные подписки, `speedtest2.env`
- результат установки/настройки через веб-форму). Если на роутере есть
сеть и в Entware стоит git - вместо `scp` можно `git clone`/`git pull`
прямо на роутере, если так уже настроено.

**Шаг 2 - применение.** Одного копирования недостаточно: новую версию
роутер подхватит только при следующем запуске speedtest2.sh. Не ждать
ближайшего cron (до трёх часов), а применить сразу:

```sh
ssh -p <порт SSH, если не 22> root@<IP роутера>
sh /opt/etc/mihomo/speedtest2.sh --force
```

`--force` запускает прогон немедленно; в том числе перегенерирует
`stats.html`, раскладывает статические файлы SPA-shell заново
(`write_stats_static()`) и переподнимает веб-сервис статистики
(`ensure_stats_httpd()` в `speedtest2.sh`), если изменились
`render_stats.awk`, `stats_cgi.sh`, `stats_httpd.py`,
`stats_index.html`/`stats_style.css`/`stats_app.js`/`stats_chart.js`/`render_progress.awk`
или настройки в `speedtest2.env`. Полный `sh install.sh` для одного
только обновления скриптов не нужен - он заново пройдёт калибровку
порога и, если гео-фильтр почему-то не сохранился, повторно запросит
его вручную.

**Шаг 3 - проверка.** Сверить хэш файла, который реально отдаёт
веб-сервис статистики, с тем, что лежит на рабочей машине - дешевле,
чем потом отлаживать в браузере несуществующий баг на старой версии
(браузерный кэш - отдельный источник той же путаницы, см. про
`Cache-Control` в CHANGELOG.md):

```sh
curl -s http://<IP роутера>:8899/app.js | md5sum
md5sum stats_app.js   # на рабочей машине, из каталога с исходниками - хэши должны совпасть
```

Если не совпали - значит либо `scp` не доехал (см. частые проблемы
выше - неверный порт, `sftp-server`), либо не был вызван
`speedtest2.sh --force` и не прошёл ближайший cron.

### Проверка обновлений и раскатка через curl (`--check-update`/`--update-core`/`--update-stats`)

Помимо ручного `scp` (см. раздел выше), в `speedtest2.sh` уже есть
встроенный механизм обновления прямо с GitHub по HTTPS - без `git` на
роутере и без ручного переноса файлов.

**Проверить, есть ли что-то новее того, что установлено** (ничего не
меняет на диске, только читает и печатает результат):

```sh
sh /opt/etc/mihomo/speedtest2.sh --check-update
```

Команда сверяет две независимые версии с файлом `VERSIONS` в репозитории
на GitHub (сначала `raw.githubusercontent.com`, при недоступности -
зеркало на `cdn.jsdelivr.net`, без всякой настройки с вашей стороны):

- `core` - `speedtest2.sh`, `install.sh`, `setup.sh`, `version_check.sh`,
  `detect_ua.sh`, `render_config.awk`, `existing_config.awk`,
  `config.example.yaml`, `prep.awk`, `providers.awk`,
  `node_stats_update.awk`, `sub_convert.awk` - весь набор, который
  исполняется на роутере (ежедневный цикл спидтеста и разовые/повторные
  install.sh/setup.sh), а не только файлы самого спидтеста;
- `stats` - `render_stats.awk`, `stats_cgi.sh`, `stats_run.sh`,
  `stats_httpd.py`, `stats_index.html`, `stats_style.css`,
  `stats_app.js`, `stats_chart.js`, `render_progress.awk`.

Печатает "core: установлена версия N, доступна M" (или "... это
актуально") и завершается - по cron не запускается, только руками.

**Раскатать обновление** - тоже руками, отдельными командами на роутере
по SSH:

```sh
ssh -p <порт SSH, если не 22> root@<IP роутера>
sh /opt/etc/mihomo/speedtest2.sh --update-core
sh /opt/etc/mihomo/speedtest2.sh --update-stats
```

Каждая команда скачивает весь свой набор файлов (см. списки выше) во
временный каталог, проверяет каждый файл на синтаксис (`sh -n` для
`.sh`, пробный разбор `awk -f ... /dev/null` для `.awk`, `python3 -m
py_compile` для `.py`, если `python3` вообще есть на роутере) и только
если ВСЕ прошли проверку - переносит их на место, сохранив резервную
копию каждого файла рядом (`*.bak-ГГГГММДДЧЧММСС`). Если хотя бы один
файл не скачался или не прошёл проверку - обновление не выполняется
целиком, старые файлы остаются как были. Это защита от битого/усечённого
файла при обрыве сети, а не от подмены содержимого - подписи или сверки
хэша с доверенным источником нет (см. `TODO.md`).

`--update-stats` применяет изменения немедленно: перегенерирует
`stats.html` и переподнимает веб-сервис статистики (`stop_stats_httpd`
+ `ensure_stats_httpd`), не дожидаясь cron - иначе обновлённый
`stats_httpd.py` продолжил бы молча работать под старым уже запущенным
процессом. Это единственный постоянно работающий процесс среди всех
обновляемых файлов, поэтому перезапуск нужен только здесь.

`--update-core` перезапуска не требует - ни один файл из группы `core`
не работает как постоянный сервис, каждый читается с диска заново при
следующем вызове: `speedtest2.sh` - на ближайшем cron либо ручном
`speedtest2.sh --force`, `install.sh`/`setup.sh` (и их общий
инструментарий `version_check.sh`/`detect_ua.sh`/`render_config.awk`/
`existing_config.awk`/`config.example.yaml`) - при следующем ручном
запуске (`--recalibrate`, пересборка подписок и т.п.). Пока такого
запуска не было - на роутере продолжает исполняться старая версия, это
ожидаемо, а не незамеченный сбой.

**Важно: пока репозиторий `f0nwa/mihomo-speedtest` на GitHub приватный.**
`raw.githubusercontent.com`/`cdn.jsdelivr.net` отдают приватным
репозиториям анонимным запросам 404 - ровно так, как если бы сеть
роутера была ограничена: `--check-update`/`--update-core`/`--update-stats`
честно напишут в лог, что источник недоступен, и завершатся с ошибкой,
хотя на самом деле дело не в сети. Сам механизм обновления - обычный
неаутентифицированный HTTPS GET (`curl`/`busybox wget`), а не `git`,
поэтому ключ авторизации GitHub (SSH-деплой-ключ, токен) тут не
поможет - единственные варианты: сделать репозиторий публичным, либо
переопределить `UPDATE_SOURCE_BASE`/`UPDATE_MIRROR_BASE` (переменные
окружения `speedtest2.sh`) на собственный источник, отдающий те же
файлы по обычному HTTP(S) без авторизации (например, свой веб-сервер
или прокси перед приватным репозиторием).

Если сеть роутера ограничена и оба адреса (основной и зеркало)
недоступны по любой другой причине, все три команды точно так же
честно напишут об этом в лог и завершатся с ошибкой - это не авария,
основной функциональности (сам спидтест и веб-статистика) недоступность
GitHub не касается. Для HTTPS нужен `curl` (или `busybox wget`, если
`curl` не установлен) с рабочими корневыми сертификатами - если на
роутере их нет, тот же результат: источники будут выглядеть недоступными.

## Режимы Mihomo

Mihomo поддерживает три режима:

| Режим | Поведение |
|---|---|
| `Rule` | Проверяет список `rules` и направляет каждый сервис по своей группе. |
| `Global` | Игнорирует `rules` и отправляет весь трафик через один вариант, выбранный в группе `GLOBAL`. |
| `Direct` | Игнорирует `rules` и отправляет весь трафик напрямую. |

В `config.example.yaml` параметр `mode` не указан. Для Mihomo режим по умолчанию - `rule`, поэтому конфигурация работает по правилам. Чтобы закрепить это явно, в начало файла можно добавить:

```yaml
mode: rule
```

### Что такое `GLOBAL`

`GLOBAL` - встроенная группа Mihomo. В файле `config.example.yaml` её нет: ядро создаёт её автоматически и заполняет доступными прокси и группами. Поэтому `GLOBAL` отображается в панели управления, даже если это имя не встречается в YAML.

Выбор внутри `GLOBAL` действует только в режиме `Global`:

- `DIRECT` отправляет весь трафик напрямую;
- конкретный прокси отправляет весь трафик через этот узел;
- `🚀Auto-Best` отправляет весь трафик через выбранный этой группой узел;
- `Заблок. сервисы` отправляет весь трафик через выбранный внутри неё вариант.

В режиме `Rule` выбор внутри `GLOBAL` ни на что не влияет. Трафиком управляют группы, указанные в `rules`.

В режиме `Global` перестают работать все правила из конфига. В частности:

- реклама не блокируется правилом `adlist@domain`;
- российские домены не направляются отдельно через `DIRECT`;
- YouTube, Telegram, CDN и остальные сервисы не используют свои группы;
- последнее правило `MATCH,DIRECT` тоже не применяется.

Для повседневной работы этого конфига следует использовать режим `Rule`. Режим `Global` пригодится как временный способ направить через прокси вообще весь трафик, например для проверки маршрутизации или доступа к сайту, которого ещё нет в правилах.

Подробнее: [режимы работы Mihomo](https://wiki.metacubex.one/en/config/general/#operation-mode) и [встроенная группа `GLOBAL`](https://wiki.metacubex.one/en/config/proxy-groups/built-in/).

## Группы сервисов

Конфиг содержит отдельные группы для следующих категорий:

- видео и медиа: `YouTube`, `Twitch`, `TMDB`, `Spotify`, `KinoPub`, `18+`, `Torrents`;
- социальные сети и мессенджеры: `Discord`, `Telegram`, `Reddit`, `Twitter`, `Meta`;
- платформы: `AI`, `Apple`, `Google`, `Microsoft`, `Steam`, `Zoom`;
- устройства и производители: `PlayStation`, `BambuLab`, `Dell`, `intel`;
- инфраструктура и диагностика: `CDN`, `Speedtest`, `IP Detect`;
- прочие выбранные домены: `other`.

Выбор группы сохраняется благодаря параметру `profile.store-selected`. После перезапуска Mihomo не должен возвращать все группы к первому варианту.

## Провайдеры

Прокси загружаются из провайдеров. В шаблоне `config.example.yaml` (для ручной правки) они называются `provider-a`, `provider-b` и `provider-c` - имя можно дать любое. При автоматической установке через `setup.sh` (см. раздел [Автоматическая установка](#автоматическая-установка)) каждому провайдеру вместо этого предлагается осмысленное имя - перенесённое старое или собранное по домену подписки. Подписки обновляются раз в час. Проверка доступности выполняется раз в 300 секунд через `http://www.gstatic.com/generate_204`, заданный общим якорем `gstatic-health-check` (см. [Интервалы проверок доступности](#интервалы-проверок-доступности)) - отдельно от провайдера `fast`, у которого свой профиль проверки.

Правила доменов и IP-адресов загружаются из внешних MRS-списков. Интервал их обновления - 86 400 секунд, то есть одни сутки.

### Подбор User-Agent для новой подписки

Панели подписок часто отдают разный формат ответа в зависимости от `User-Agent`: JSON для v2rayNG/xray (Mihomo как `proxy-providers` его не понимает), полный clash YAML для clash.meta/mihomo/clash-verge, укороченный YAML для старых ClashX/ClashforWindows или base64-список нод для Shadowrocket/Quantumult X/Surge. Прежде чем добавлять новую подписку в `config.yaml` по образцу `config.example.yaml`, проверьте, под каким `User-Agent` сервер отдаёт полный clash YAML:

```
sh detect_ua.sh "https://ссылка-на-вашу-подписку"
```

Скрипт перебирает частые клиентские `User-Agent` и для каждого печатает HTTP-код, размер ответа и определённый формат. Строку `clash YAML, полный (подходит для mihomo proxy-providers)` и стоит использовать в `header.User-Agent` провайдера. Инструмент не устанавливается на роутер - это разовая помощь при сборке конфига на рабочей машине с доступом в интернет и curl.

Если после перебора ни один `User-Agent` не даёт полный clash-yaml (панель всегда отдаёт base64-список ссылок) - для протокола vless есть `sub_convert.awk`, он встроен в `speedtest2.sh` и работает автоматически, без ручной настройки.

## Сетевые параметры

- `redir-port: 5000` - порт прозрачного проксирования через REDIRECT;
- `tproxy-port: 5001` - порт прозрачного проксирования через TPROXY;
- `allow-lan: true` - разрешает подключения к Mihomo из локальной сети;
- `external-controller: 0.0.0.0:9090` - открывает API управления на всех сетевых интерфейсах;
- `external-ui: ./zash` - каталог веб-панели Zashboard;
- `sniffer.enable: true` - помогает определять домен по HTTP- и TLS-трафику;
- `STATS_HTTP_PORT` (по умолчанию 8899) - порт отдельного веб-сервиса статистики speedtest2 (`stats.html` и форма настройки `/cgi-bin/config`), см. раздел про speedtest2.sh выше.

API управления слушает всю локальную сеть, а параметр `secret` в конфиге не задан. Не открывайте порт `9090` в интернет и ограничьте доступ к нему правилами межсетевого экрана. То же самое касается порта веб-сервиса статистики (по умолчанию 8899, слушает `0.0.0.0`) - `stats.html` на нём отдаётся без пароля всем, кто до него достучится, а форма настройки (`/cgi-bin/config`) защищена паролем только если он явно задан через `STATS_AUTH_USER`/`STATS_AUTH_PASS`; порт всё равно не должен быть виден из интернета.

## Проверка результата

```sh
curl -s http://127.0.0.1:9090/version
curl -s http://127.0.0.1:9090/providers/proxies | head -c 400
grep -cE '^- ' /opt/etc/mihomo/fast.yaml
```

Последняя команда считает ноды в `fast.yaml` (считать по `^- name:`
нельзя - библиотека yaml сортирует ключи внутри ноды, и `name` не всегда
идёт первым). Достижимость конкретного сайта через конкретную ноду:

```sh
curl -s 'http://127.0.0.1:9090/proxies/<имя ноды>/delay?url=https://example.com&expected=200'
```

Запрос требует имя ноды, а не группы - ответ "Resource not found"
означает, что ноды нет в `/proxies`, тогда тест гоняется через
группу-обёртку.

## Известные проблемы

- **Применение конфига.** Только `xkeen -restart`. API-reload роняет ядро.
- **Валидация перед рестартом.** `mihomo -t` ловит опечатки в yaml и
  неизвестные поля, но не ловит ссылку на несуществующую группу в
  правилах - такой конфиг стартует, а трафик уходит мимо.
- **Дубли имён нод.** Две ноды с одинаковым именем mihomo как конфиг не
  читает вовсе, как провайдер - молча схлопывает в одну.
- **Разные отступы в кэшах подписок.** Одна панель пишет ноды с отступом
  2, другая с отступом 4 - свалить их в один список нельзя, `prep.awk`
  это выравнивает.
- **Inline-map в подписке.** Записи вида `- {name: ..., type: ...}`
  замерщик не разбирает: `prep.awk` вернёт ошибку, а `speedtest2.sh`
  оставит прежний `fast.yaml`. Нужен блочный clash-yaml.
- **Base64-подписки (vless).** Замерщик умеет разбирать base64-подписку
  vless-ссылок через `sub_convert.awk` (см. `SUB_CONVERT` в шапке
  `speedtest2.sh`) - конвертирует её в clash-yaml перед `prep.awk`.
  Другие протоколы (trojan, ss и т.п.) в base64-подписке всё ещё не
  разбираются - такая нода в base64-подписке останется невидимой. Прежде
  чем полагаться на конвертер, стоит проверить `detect_ua.sh`
  (см. раздел "Подбор User-Agent для новой подписки") - часто панель
  отдаёт полный clash-yaml под другим `User-Agent`, и тогда конвертер
  вообще не нужен.
- **Общие CDN перехватывают чужой трафик.** Правила по rule-set вида
  `amazon` или `cloudflare` ловят кучу постороннего - если у вас есть
  устройство со своим CDN (умная колонка, 3D-принтер), заведите для него
  DIRECT-правило выше по списку.
- **Не всё чинится VPN.** Некоторые сайты режут датацентровые IP -
  через ноды подписок могут не открываться вовсе, хотя напрямую
  отвечают нормально. Стоит проверять обе стороны, прежде чем заводить
  домен в VPN-список.
- **DNS-секция.** В примере конфига она выключена, резолвит системный
  резолвер роутера. Правила по доменам всё равно работают - mihomo
  определяет домен по SNI из TLS-рукопожатия через sniffer. Включение
  DNS в mihomo требует отдельной проработки схемы.
- **Подписки умирают тихо.** Не от блокировок, а от самих сервисов:
  протухший токен, привязка к устройству, панель, которая вместо пула
  отдаёт одну ноду. Симптом - кэш в `proxy-providers/` перестаёт
  обновляться, а в веб-морде провайдер показывает старую дату.
- **Перед ребутом роутера убедиться, что накопитель пишет.**
  `touch /opt/etc/mihomo/.wtest && rm /opt/etc/mihomo/.wtest`. Если
  файловая система ушла в read-only, mihomo продолжит работать из
  памяти, а после перезагрузки поднимется старый конфиг.

## Что дальше

- Свои домены в VPN: секция `user@classical` в конфиге, синтаксис
  правил - https://wiki.metacubex.one/ru/config/rules/
- Статические ноды вне подписок (Hysteria2, AmneziaWG) кладутся в
  секцию `proxies:` и попадают в группы через `include-all-proxies`.
  Замерщик тоже их проверяет: `install.sh` кладёт сам `config.yaml`
  первым источником в `SOURCES` (`speedtest2.env`), перед кэшами
  подписок - так что и статические ноды участвуют в замере скорости
  наравне с нодами из подписок.
- Бэкап: `/opt/etc/mihomo` целиком плюс `crontab -l`. Busybox на роутере
  умеет только распаковывать tar, создавать архив нечем - копировать по
  scp как есть.

## Конфиденциальность

В рабочем `config.yaml` находятся адреса подписок и пароли статических прокси, поэтому файл исключён из Git. Не снимайте это исключение и не публикуйте рабочий конфиг. Если он уже был опубликован, замените ссылки подписок и пароли у провайдеров.
