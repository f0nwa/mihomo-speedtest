# Формат манифеста управляемого обновления

## Версии и заголовок

Генератор выпускает формат 2. Обновлятор версии 6 также читает формат 1
локального прототипа; первый опубликованный управляемый релиз должен иметь
формат 2. Неизвестный формат отклоняется целиком. Версия обновлятора задана
константой UPDATER_VERSION в update.sh, отдельно от версии релиза.

Каждое поле заголовка встречается ровно один раз:

```text
FORMAT_VERSION=2
RELEASE_VERSION=9
RELEASE_TAG=v9
MIN_UPDATER_VERSION=4
CONFIG_SCHEMA_VERSION=1
```

Версии - десятичные целые неотрицательные числа без суффиксов. RELEASE_TAG
обязателен для формата 2, начинается с буквы ASCII или цифры, далее допускает
буквы ASCII, цифры, точку, дефис и подчёркивание; последовательность `..`
запрещена. Это точное имя неизменяемого GitHub-тега, а не ветка main.

В --check и --plan минимальная версия проверяется установленным CLI.
--prepare получает четыре файла свежего обновлятора из точного RELEASE_TAG,
проверяет размер, SHA256 и синтаксис, затем запускает его из /tmp.
Минимальная версия проверяется уже свежим CLI. --verify-plan запускается
через сохранённый проверенный движок плана, поэтому обновление установленного
CLI для этой проверки не требуется.

## Строки каталога

```text
COMPONENT|updater|Обновлятор
NOTE|updater|Обновление инструмента без перезапуска служб
FILE|updater|update.sh|/opt/etc/mihomo/update.sh|123|<64 символа sha256>|0755|sh
DEPENDS|web|speedtest-runtime
CONFLICT|legacy-web|web
ACTION|web|restart-web
```

Пример FILE поясняет поля; вместо `<64 символа sha256>` генератор записывает
реальную сумму, а вместо 123 - реальный размер в байтах.

- COMPONENT объявляет уникальный id по шаблону `[a-z][a-z0-9-]*` и непустое
  пользовательское описание. FILE и ACTION следуют после своего COMPONENT.
- NOTE содержит одну непустую заметку для каждого компонента формата 2:
  влияние на работу и необходимость перезапуска. Заметки показываются в
  текстовом плане и JSON. Символ `|` внутри описаний и заметок запрещён.
- DEPENDS добавляет обязательный компонент. Весь граф проверяется на циклы,
  даже если цикл находится вне выбранного набора.
- CONFLICT симметричен. Обе ссылки должны быть известными разными компонентами.
  Одновременный выбор запрещён, в том числе после добавления зависимостей.
  Каталог может содержать несовместимые альтернативы. Отсутствие CONFLICT
  означает отсутствие объявленных несовместимостей.
- FILE: компонент, исходный относительный путь, абсолютное назначение,
  размер, SHA256 в нижнем регистре, режим 0644/0755 (допускается без ведущего
  нуля), проверка sh/awk/py/none. Пути используют ASCII-буквы, цифры,
  `_`, `.`, `/`, `-`; пустые сегменты, `.`/`..` и завершающий `/` запрещены.
- Разрешены назначения внутри /opt/etc/mihomo, кроме config.yaml и .update
  с её содержимым; вне него только /opt/etc/init.d/S80speedtest-stats.
  Подготовка отвергает символические ссылки назначения и родителей.
- ACTION допускает только restart-web/migrate-config/restart-mihomo.
  Замена файлов speedtest-runtime не требует restart-mihomo. Это действие
  предназначено для будущей миграции рабочего конфига.

Формат 1 не содержит RELEASE_TAG, NOTE и CONFLICT. Пустые строки допустимы,
комментарии в готовом манифесте не допускаются. Неизвестные строки, неверное
число полей и повторные поля заголовка запрещают весь манифест.

## Декларация и генерация

release/components.txt содержит те же COMPONENT/NOTE/DEPENDS/CONFLICT/ACTION,
а FILE имеет шесть полей: компонент, исходник, назначение, режим, проверка.
Пустые строки и комментарии, начинающиеся с `#`, допускаются только здесь.

```sh
sh release/generate_manifest.sh 9 4 1 v9 > /tmp/manifest.txt
```

Четвёртый аргумент необязателен; по умолчанию тег равен `v<release_version>`.
Генератор вычисляет размеры и суммы и проверяет весь каталог через
update_plan.awk с VALIDATE_ONLY=1. Конфликтующие альтернативы не выбираются
одновременно. При ошибке stdout пуст; перенаправляйте результат во временный
файл, чтобы ошибка генерации не обнулила прежний манифест.

Установщик размещает updater, installer и config-tools на роутере, включая
uninstall.sh и переходный VERSIONS в installer. Рабочий config.yaml не
перезаписывается этими компонентами. Генератор и декларация остаются на
компьютере разработчика.

## Подготовка и повторная проверка

```sh
sh /opt/etc/mihomo/update.sh --prepare --components=web --format=json
sh /opt/etc/mihomo/update.sh --verify-plan "$plan_id" --format=json
sh /opt/etc/mihomo/update.sh --discard-plan "$plan_id"
```

Перед проверкой задайте переменную `plan_id` равной 64-значному идентификатору
из результата подготовки.
--plan показывает предварительный идентификатор без загрузки файлов.
--check загружает только манифест. Подготовка сохраняет выбранные файлы,
зависимости и свежий движок в /tmp/mst-update-plans/<plan_id> с правами 0700.
План действует 24 часа, исчезает при перезагрузке; просроченные планы удаляются
при следующей подготовке. --discard-plan удаляет только указанный план.
Незавершённые рабочие каталоги очищаются при выходе.

Идентификатор связывает источник и сумму манифеста, канонический набор
компонентов, корень установки, содержимое и права управляемых файлов,
config.yaml, установленный манифест и метаданные схемы. Проверка повторно
получает latest: изменение релиза или локального снимка требует нового плана.
Также проверяются размер, SHA256, режим и синтаксис каждого сохранённого файла.
Содержимое конфига не выводится. Для локально изменённых файлов проверка
требует --confirm-local; это подтверждение не сохраняется как разрешение
на дальнейшую запись.

Манифест ограничен 256 КиБ, каждый файл bootstrap - 1 МиБ, файл полезной
нагрузки - 8 МиБ, выбранный набор - 32 МиБ. До загрузки проверяется свободное
место. Shell проверяется через sh -n, AWK разбирается с защитой от исполнения
BEGIN/END, Python через compile без создания pycache.
Штатная загрузка требует curl с поддержкой HTTPS и исправные сертификаты.
Перенаправление с HTTPS на HTTP запрещено. HTTP допускается только для
localhost/127.0.0.1 с явным портом и без перенаправлений; userinfo, параметры
запроса и фрагменты URL запрещены. UPDATE_HTTP_CMD задаёт доверенный внешний
транспорт для офлайн-проверок. UPDATE_TARGET_ROOT позволяет подготовить
альтернативную установку: /opt/... отображается в <root>/opt/...; корень
включён в идентификатор. На роутере эти переменные обычно не задаются.

Подготовка не пишет в /opt и не перезапускает службы. Понижение версии
релиза или схемы блокируется. Рост схемы готовит миграцию по правилам ниже;
применение миграции выполняется общей транзакцией по правилам части 3.3.

## Применение, откат и восстановление

```sh
sh /opt/etc/mihomo/update.sh --apply "$plan_id" --format=json
sh /opt/etc/mihomo/update.sh --rollback-last
sh /opt/etc/mihomo/update.sh --recover
```

--apply заново проверяет подготовленный план под общей блокировкой. Для
локально изменённых файлов нужен отдельный --confirm-local при применении;
предыдущее подтверждение --verify-plan не сохраняется.
Файлы публикуются через проверенный временный файл рядом с назначением и mv.
Установленный манифест содержит выбранные новые компоненты вместе со старыми
невыбранными. Рабочий config.yaml не меняется, installer/setup/speedtest и
перезапуск Mihomo не запускаются.

В .update сохраняются компактный transaction.txt и один комплект rollback.
Перед сменой этапа и после публикации журнала выполняется проверяемый sync;
комплект отката продвигается до удаления предыдущего.
Старые файлы резервируются жёсткими ссылками, при невозможности - копиями.
До успешной проверки нового состояния предыдущий комплект отката сохраняется.
После ошибки применения восстанавливаются все файлы операции и старый
манифест; добавленные файлы удаляются. Повреждённая резервная копия запрещает
восстановление до первой записи. Ошибка отката оставляет журнал и отличается
от ошибки обновления.

Веб-служба перезапускается один раз при изменении её выбранных файлов;
restart и check ограничены UPDATE_ACTION_TIMEOUT (по умолчанию 15 секунд).
После отката выполняются действия восстановленного состояния.
Управляемое обновление поддерживает уже установленную веб-службу: если старого
S80speedtest-stats нет и требуется restart-web, применение отклоняется до
постоянных записей. Первичная установка службы выполняется через install.sh.
--rollback-last и --recover работают без сети через сохранённый проверенный
движок. Общая блокировка находится в /tmp/mst-update-plans/.lock. Захват устаревшей
блокировки сериализован через .lock.reap. Если процесс принудительно завершён
во время этой короткой очистки и .lock.reap остался, автоматическая запись
запрещена: проверьте владельца в .lock.reap/pid перед ручным удалением либо
перезагрузите роутер, чтобы очистить RAM.
Незавершённый журнал блокирует новое планирование, подготовку и
применение. --recover откатывает незавершённое применение либо завершает
публикацию состояния, которое уже прошло проверку здоровья.

Права читаются через GNU/BSD stat либо POSIX ls: минимальный BusyBox stat
на целевом Keenetic не поддерживает форматированный вывод.
На Keenetic необходима отдельная приёмка перезапуска реальной службы и
восстановления после отключения питания. Изолированные тесты не заменяют
эту проверку.
На 2026-09-18 изолированный прогон на целевом Keenetic прошёл: 14 прямых
проверок, 16 CLI-тестов, 9 тестов восстановления; на USB/ext4 проверены
жёсткая ссылка, атомарная замена и откат малого файла.
Первый публичный релиз v1 опубликован 2026-09-18 из коммита
5a5eaf9089557fb25eacc430c5f637316b642548: RELEASE_VERSION=1,
MIN_UPDATER_VERSION=4, CONFIG_SCHEMA_VERSION=1. В нём 29 файлов проекта,
manifest.txt и SHA256SUMS. Репозиторий открыт для загрузки без токена.
На роутере прошли --check, --prepare и --verify-plan для updater; все четыре
файла актуальны, действий над службами нет. Проверочный план удалён из RAM.
Боевые файлы и службы изолированным прогоном не изменялись.

## Ручное обновление несовместимого bootstrap

Версия 4 добавляет update_transaction.sh в bootstrap. Установленный bootstrap
версии 3 требует однократного ручного обновления четырёх файлов.
Если стабильный bootstrap не может прочитать релиз, возьмите проверенные
владельцем update.sh, update_plan.awk, update_prepare.sh и update_transaction.sh из локального
репозитория. На компьютере владельца:

```sh
cd /Volumes/SAMSUNG/SynologyDrive/mihomo/mihomo_fonwa
ssh -p 222 root@192.168.10.1 'mkdir -p /tmp/mihomo-updater-manual' &&
scp -O -P 222 update.sh update_plan.awk update_prepare.sh update_transaction.sh root@192.168.10.1:/tmp/mihomo-updater-manual/ &&
ssh -p 222 root@192.168.10.1 'set -eu
stage=/tmp/mihomo-updater-manual
trap '\''rm -rf "$stage"; rm -f /opt/etc/mihomo/.update.sh.manual /opt/etc/mihomo/.update_plan.awk.manual /opt/etc/mihomo/.update_prepare.sh.manual /opt/etc/mihomo/.update_transaction.sh.manual'\'' EXIT
sh -n "$stage/update.sh"
sh -n "$stage/update_prepare.sh"
sh -n "$stage/update_transaction.sh"
printf "BEGIN { exit 0 } END { exit 0 }\n" > "$stage/guard.awk"
awk -f "$stage/guard.awk" -f "$stage/update_plan.awk" </dev/null
for name in update_plan.awk update_prepare.sh update_transaction.sh update.sh; do
  cp "$stage/$name" "/opt/etc/mihomo/.$name.manual"
  case "$name" in *.sh) chmod 0755 "/opt/etc/mihomo/.$name.manual" ;; *) chmod 0644 "/opt/etc/mihomo/.$name.manual" ;; esac
  mv "/opt/etc/mihomo/.$name.manual" "/opt/etc/mihomo/$name"
done'
```

Команды проверяют синтаксис, но не заменяют аудит исходников. Пофайловая
атомарная замена здесь не является транзакцией четырёх файлов; после прерывания
повторите перенос всех четырёх файлов.

Официальные релизы должны быть доступны по HTTPS без токена. Проверка
SHA256 подтверждает соответствие манифесту; цифровой подписи пока нет.

## Неинтерактивный мигратор: часть 3.1

migrate_config.sh и migrate_config.awk собирают кандидат из старого конфига
и нового шаблона. В части 3.2 они включены в config-tools и установщик;
bootstrap по-прежнему состоит из четырёх файлов обновлятора.
Пример на компьютере с заранее подготовленной копией старого конфига:

```sh
sh migrate_config.sh --source /tmp/current-config.yaml \
  --template config.example.yaml --output /tmp/config-candidate.yaml \
  --report /tmp/config-migration.txt
```

Выход и отчёт допускаются только в /tmp (на macOS также /private/tmp),
на Keenetic это RAM. Входы читаются, символические ссылки в конечных файлах
отклоняются, выход не может совпадать со входом или отчётом. Файлы имеют
режим 0600. Вход ограничен 1 МиБ, кандидат - 4 МиБ, отчёт - 64 КиБ;
запись AWK дополнительно ограничена ulimit. При ошибке существующий кандидат
сохраняется. Отчёт публикуется первым: при ошибке последующего mv он уже
может быть новым, поэтому использовать результат можно только при коде 0.

Поддерживается блочная структура конфига проекта, а не произвольный YAML.
HTTP-подписки с простыми именами [A-Za-z0-9_-] переносятся целыми блоками,
включая URL, UA и дополнительные настройки. Известный файловый fast берётся
из нового шаблона; HTTP-подписка с именем fast отклоняется. Другие файловые
провайдеры отмечаются REVIEW. DNS и статические proxies сохраняются текстом,
пустой proxies: [] не заменяется демонстрационными узлами. У статического
узла name должен быть первым полем. Списки ссылок групп на статические
узлы шаблона согласуются с перенесёнными именами, включая запятые в кавычках.

Локальные поля, сохраняемые явно: log-level, allow-lan, redir-port,
tproxy-port, port, socks-port, mixed-port, bind-address, find-process-mode,
unified-delay, external-controller, external-ui, external-ui-url, secret,
authentication, skip-auth-prefixes, lan-allowed-ips, lan-disallowed-ips,
ipv6, profile, sniffer, routing-mark. Значения не интерпретируются.
anchors, proxy-groups, rule-providers и rules берутся из нового шаблона;
различия отмечаются REVIEW. Неизвестные верхнеуровневые ключи не переносятся
и отмечаются REVIEW. Дубли ключей, неподдерживаемые flow-формы providers/proxies,
неверные маркеры и ссылки на отсутствующие YAML-якоря блокируют результат.
Проверка якорей пропускает кавычки, комментарии и тела блочных скаляров.

Отчёт содержит PRESERVED|тип|имя и REVIEW|тип|имя без значений секретов.
REVIEW требует внимания перед будущим применением. Эта часть не вызывает
сеть, setup.sh, detect_ua.sh, Mihomo или XKeen. Интеграция ниже проверяет
кандидат через Mihomo; транзакция рабочего config.yaml описана в части 3.3.


## Кандидат в плане обновления: часть 3.2

При CONFIG_SCHEMA_VERSION выше установленной схемы (без метаданных - 1)
план автоматически включает виртуальный active-config с зависимостью
config-tools. Манифест не может объявить active-config или config.yaml как
FILE. При равной схеме миграция не запускается. Подготовка появилась в CLI
версии 5; применение требует версии 6.

--prepare скачивает инструменты и шаблон точного релиза, проверяет размер,
SHA256 и синтаксис, затем запускает проверенный мигратор в RAM. Копия старого
конфига должна совпадать с хешем снимка. Итоговый plan_id дополнительно
связывает candidate.yaml, config-source.yaml, migration-report.txt,
config-diff.json и config-info.txt. Поэтому при миграции используйте ID из
--prepare, а не предварительный ID из --plan. --verify-plan повторяет сборку,
diff и mihomo -t, проверяет исходный снимок и все сохранённые результаты.

```sh
sh /opt/etc/mihomo/update.sh --prepare --components=config-tools --format=json
# plan_id берётся из результата подготовки:
sh /opt/etc/mihomo/update.sh --show-config-diff "$plan_id" --format=json
sh /opt/etc/mihomo/update.sh --show-config-diff "$plan_id" --full-config-diff
sh /opt/etc/mihomo/update.sh --verify-plan "$plan_id" --confirm-config
```

Обычный diff - JSON-массив разделов {section, change}; change равен added,
removed или changed. Он не содержит значений, URL, имён узлов и секретов и
пригоден для будущего веб-интерфейса. Полный unified diff доступен только
через --full-config-diff в текстовом формате и может содержать секреты.
Отсутствующая/изменённая сохранённая сумма config-sha256 или REVIEW требуют
--confirm-config при проверке плана. --confirm-local относится к изменениям
файлов инструментов и не заменяет это подтверждение. Просмотр diff доступен
до подтверждения. Подтверждение не сохраняется как разрешение на применение.

Проверка запускает отдельный mihomo -t -d <RAM-каталог> -f <кандидат>.
Переменные SAFE_PATHS, SKIP_SAFE_PATH_CHECK и CLASH_* переопределения входа,
домашнего каталога и хуков очищаются. Существующие GEO-базы копируются в RAM:
не более 32 МиБ каждая и 64 МиБ суммарно; проверяется свободное место.
Запись одного файла ограничена ulimit -f 4096; вывод скрыт в RAM-журнале.
Таймаут по умолчанию 30 секунд, UPDATE_CONFIG_TEST_TIMEOUT допускает 1-120;
после таймаута тестовый процесс завершается KILL. UPDATE_MIHOMO_BIN задаёт
доверенный бинарник для тестовых фикстур. Каталог проверки очищается после
процесса; кандидат не должен измениться во время проверки. Семантика -t и
ограничения путей сверены с [main.go](https://github.com/MetaCubeX/mihomo/blob/v1.19.29/main.go)
и [constant/path.go](https://github.com/MetaCubeX/mihomo/blob/v1.19.29/constant/path.go).

--apply для плана с active-config использует транзакцию, описанную ниже.
Эта доработка сама по себе не публикует новый релиз и не обновляет роутер.

## Применение миграции: часть 3.3

```sh
sh /opt/etc/mihomo/update.sh --apply "$plan_id" --confirm-config --format=json
# После ошибки или прерывания сначала восстановите транзакцию:
sh /opt/etc/mihomo/update.sh --recover --format=json
# Вернуть весь последний успешно установленный набор:
sh /opt/etc/mihomo/update.sh --rollback-last --format=json
```

Подтверждение на --verify-plan не переносится на --apply: при необходимости
--confirm-config и --confirm-local задаются заново. Проверка кандидата и
входного снимка повторяется под общей блокировкой. Рабочий config.yaml
запрещён как FILE релиза и не скачивается готовым с GitHub.

Комплект отката содержит отдельные фиксированные записи CONFIG, SCHEMA и HASH
для конфига, config-schema-version и config-sha256; либо все три, либо ни одной.
Имена, хеши, размеры, режимы, набор действий и пересечения назначений с
временными путями проверяются до записи. Исходный конфиг обязан существовать.
Конфиг сохраняет прежний режим; новые метаданные имеют 0600. Отсутствовавшие
метаданные удаляются при откате, существовавшие восстанавливаются с режимами.

До постоянной записи проверяются наличие исполняемого XKeen, таймауты и
поддерживаемость параметров локального API в исходном конфиге и кандидате.
После подготовки проверенного backup публикуется APPLY_PENDING. Затем
атомарно заменяются выбранные файлы, кандидат, схема, сумма и установленный
манифест. Один xkeen -restart применяется к опубликованному конфигу, далее
проверяются процесс Mihomo и GET /version локального API. Готовность API
ожидается ограниченное время. Если нужно, веб-служба перезапускается отдельно
после Mihomo. COMMIT записывается после успешных завершающих действий.

Ошибка после начала записи восстанавливает весь набор и старые метаданные,
затем один раз перезапускает XKeen со старым конфигом и проверяет здоровье.
Ошибка восстановления сохраняет журнал и блокирует новые обновления.
--recover работает без сети и RAM-плана: движок из четырёх файлов проверяется
по сохранённому манифесту. APPLY_PENDING откатывается; COMMIT завершает
сохранение уже проверенного нового состояния без повторного перезапуска.
Повторный сбой во время отката может потребовать повторного restart при
следующем recover; гарантия одного внешнего запуска через потерю питания
не предоставляется.

UPDATE_ACTION_TIMEOUT ограничивает каждый внешний запуск (по умолчанию 15
секунд), UPDATE_HEALTH_TIMEOUT - ожидание здоровья (по умолчанию 15 секунд);
оба принимают 1-300. Вывод остаётся в ограниченных RAM-журналах, затем удаляется.
При таймауте/отмене завершается дерево запуска; при успешном restart новые
служебные процессы сохраняются. Для фикстур UPDATE_XKEEN_BIN задаёт доверенный
исполняемый файл с аргументом -restart, UPDATE_HEALTH_CMD - доверенный файл
без аргументов. Эти переопределения на обычном роутере не требуются.
Ошибка внешнего health-командного файла запускает откат без повторных попыток.

Стандартная проверка поддерживает простой однострочный external-controller
с localhost, 127.0.0.1 или 0.0.0.0 и TCP-портом, а также простой secret.
Неоднозначные формы YAML блокируются до записи. Wildcard приводится к
127.0.0.1; Bearer передаётся curl через RAM-конфигурацию 0600, без секрета в
аргументах командной строки. Проверка отключает пользовательский curlrc и
прокси окружения, не выводит ответ API и не использует PUT /configs.

Приёмка с заменой боевого конфига, реальным перезапуском и отключением питания
требует отдельного согласования. Фиктивная RAM-установка эту приёмку не заменяет;
сам коммит не обновляет опубликованный релиз или роутер.
